## Фактическое состояние и оговорки

- React + JavaScript/JSX + Vite + обычный глобальный CSS + Lucide. Монтирование в #root, а не в #ekt-ai-chat; сборка обычного SPA.
- Стили содержат body, :root, button и другие глобальные правила. Изоляции нет.
- В src/api.js реализован POST /api/chat, а не /api/chat/message. Контракт из этого плана ещё не согласован.
- session_id создаётся при монтировании приложения и сохраняется в sessionStorage.
- Таймаут 30 секунд есть; скорость ответа реального сервера не проверена.
- Текст условий покупки может отображаться как любой текст; содержательные ответы backend не проверены.
- Ответы выводятся React как текст, без вставки HTML. Markdown и кликабельные сертификаты не поддерживаются.
- Карточки имеют название, артикул, цену и boolean наличия. Нет характеристик, численного остатка и сертификатов.
- Подтверждение добавления есть только для локальной корзины. Количество при добавлении фиксировано: 1; менять можно позже, без проверки остатка.
- POST /api/cart/confirm отсутствует полностью; отметка об отсутствии вызова без подтверждения НЕ означает готовность интеграции корзины.
- Пустая строка ответа проходит проверку; products=[] показывает стартовую заглушку вместо «ничего не найдено».
- Адаптивная страница есть, адаптивного плавающего виджета нет.
- Документация запуска и переменной VITE_API_URL есть в FRONTEND.md; инструкции встраивания отсутствуют.
- Этап приёмочного тестирования не отмечен: нужны реальные данные и проверки, одной сборки недостаточно.

## 0. Контекст задачи (для агента, кратко)

Бэкенд: Python + FastAPI (делает другой человек/агент).
Фронтенд: встраиваемый чат-виджет на сайте ekt.kz.
Пользователь пишет в чат → получает консультацию по товару/аналогам/условиям покупки →
при явном подтверждении товар добавляется в корзину → пользователю выдаётся ссылка на корзину.

Фронтенд **не должен**:
- сам ходить в `ekt.kz/api/products*` (basicAuth и работа с каталогом — зона ответственности бэкенда);
- менять корзину без явного подтверждения пользователя;
- запрашивать/хранить платёжные данные.

Фронтенд общается только со **своим бэкендом** (FastAPI), который уже инкапсулирует доступ к API ekt.kz.

## 2. Контракт с бэкендом (нужно согласовать с бэкенд-частью)

Прежде чем кодить экраны, зафиксировать API-контракт. Минимально нужны эндпоинты:

- [ ] `POST /api/chat/message` — отправка сообщения пользователя (текст + session_id + вложения) → ответ ассистента (текст + опционально структурированные блоки: карточка товара, список аналогов, кнопки подтверждения).
- [ ] `POST /api/chat/attachment` — загрузка файла (excel/word/pdf/jpeg) для анализа (фото товара, спецификация, накладная).
- [ ] `POST /api/cart/confirm` — подтверждение добавления в корзину (артикул, количество) → обновлённая корзина + ссылка на checkout.
- [ ] `GET /api/session/history?session_id=...` (опционально) — история диалога в рамках сессии.
- [ ] Формат ошибок API (код, сообщение) — единый для всех эндпоинтов.

**Действие:** зафиксировать JSON-схемы запросов/ответов в отдельном файле `api-contract.md` и держать её синхронной с бэкендом.

## 3. Этапы разработки

**Критерий готовности:** виджет открывается/закрывается, статично отображает пустой чат, не конфликтует со стилями сайта.

### Этап 2 — Обмен сообщениями с бэкендом
- [~] Отправка текстового сообщения на `POST /api/chat/message`.
- [x] Хранение `session_id` (генерируется на фронте при первом открытии, хранится в sessionStorage вкладки).
- [x] Отображение сообщений пользователя и ассистента в ленте (разные стили пузырей).
- [x] Индикатор "печатает…" / загрузка ответа.
- [x] Обработка задержки ответа (по ТЗ — единицы секунд; таймаут и сообщение об ошибке, если дольше).
- [x] Автоскролл к последнему сообщению.

**Критерий готовности:** можно написать вопрос и получить текстовый ответ от бэкенда (даже с мок-данными).

### Этап 3 — Отображение структурированных ответов
- [~] Карточка товара: название, артикул, характеристики, наличие, ссылка/файл сертификата.
- [ ] Блок "аналоги": список из карточек + краткое обоснование, почему предложен именно этот аналог (объяснимость — это must have из ТЗ).
- [x] Текстовый блок для ответов об условиях покупки (оплата/доставка/мин. партия) — обычный текст, без спецразметки.
- [ ] Рендеринг ссылок и файлов сертификатов кликабельными.

**Критерий готовности:** ответ по существующему артикулу отображается как карточка с характеристиками и (если есть) сертификатом; при нулевом остатке — блок аналогов.

### Этап 4 — Вложения от пользователя
- [ ] Кнопка/иконка "прикрепить файл" в поле ввода.
- [ ] Поддержка форматов: JPEG, Excel, Word, PDF.
- [ ] Валидация типа/размера файла на клиенте перед отправкой.
- [ ] Превью прикреплённого файла (имя + иконка/тумбнейл для фото) перед отправкой.
- [ ] Отправка на `POST /api/chat/attachment`, привязка к текущему сообщению/сессии.
- [ ] Обработка ошибки загрузки (неверный формат, файл слишком большой, сеть).

**Критерий готовности:** пользователь может прикрепить фото товара или Excel-спецификацию, файл уходит на бэкенд и попадает в контекст диалога.

### Этап 5 — Подтверждение и корзина (ключевой must-have)
- [~] Когда ассистент предлагает добавить товар — фронт показывает явный UI-элемент подтверждения (например, кнопки "Да, добавить" / "Нет") — **не текстовое "да" произвольным вводом**, чтобы исключить случайное срабатывание.
- [~] Возможность указать/изменить количество перед подтверждением, с учётом отображаемого остатка.
- [x] Без нажатия кнопки подтверждения — никаких вызовов `POST /api/cart/confirm`.
- [ ] После подтверждения — вызов API, отображение обновлённого состояния корзины в чате (что добавлено, кол-во).
- [ ] Отображение прямой кликабельной ссылки на страницу корзины/оформления заказа.
- [ ] Обработка случая "запрошенное количество больше остатка" — предупреждение до подтверждения.

**Критерий готовности:** ровно соответствует проверке из ТЗ — без явного «да, добавь» корзина не меняется; после подтверждения количество не превышает остаток; ссылка ведёт на актуальную корзину.

### Этап 6 — Обработка ошибок и edge cases
